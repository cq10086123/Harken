**关于"难度"：真正的工作量不在加音源，在于把 24 个页面从飞牛模型上摘下来（页面层 `FeiNiu*` 引用 259 处）。** 但这件事有两个特性让它风险可控：

1. **它是机械的，不是设计的** —— 见第六节，飞牛模型字段高度统一，新实体可同名镜像，页面改动退化为「改类型名 + 换一次取数调用」。

**关于"不可逆"：真正不可逆的只有两项**（DB 迁移、包名），且都有明确安全做法。其余全部 git 层面可回退。详见第九节。

### 上游 `SongEntity` 字段与 v2 预测完全一致

上游 `lib/app/state/song_state.dart` 有 `isLocal`、`sourceId`、`fileModifiedMs`、`localCoverPath`、`localAssetId`、`tagsParsed` —— **正是 v2 第五节推导出的那组字段**。这不是巧合：这些字段就是魔改时从上游剥掉的残留（第三节「免费资产」的来源）。

### 上游解决了 v2 里两个悬而未决的问题

**① Android 目录读取（v2 标为 🔴 高风险，需真机探针）**

上游 `local_music_service.dart` 用**双路径**，且两条路径的开关在 `LocalSourceSettings` 里：
- `useSystemLibrary` + `includeAlbumIds` → `PhotoManager.getAssetPathList(type: RequestType.audio)`（`:228`），MediaStore，**零新权限**
- `includePaths` → `_collectCustomFiles()`（`:574-610`）纯 `dart:io` `Directory.list(recursive: true)` + 扩展名过滤（`.mp3 .flac .wav .m4a .aac .ogg .opus .alac .wma`）

**结论：不需要 `MANAGE_EXTERNAL_STORAGE`，也不需要 SAF `content://` 处理。** v2 的 A/B/C 三选一变成「A + 自定义目录递归」的组合，且上游已验证可行。风险等级从 🔴 降为 🟡。

**② 三端支持（用户新增要求）**

上游 `lib/` 全仓只有 3 个文件做平台分支（`android_platform_service.dart` / `media_notification_service.dart` / `song_download_service.dart`），音源层代码本身与平台无关。但：

| 平台 | 本地音源取材路径 | 说明 |
| :--- | :--- | :--- |
| Android | MediaStore（`photo_manager`）+ 自定义目录递归 | 上游原样可用 |
| iOS | 媒体库（`photo_manager` 支持）+ 文件 App 授权目录 | 需验证 `photo_manager` 的 `RequestType.audio` 在 iOS 返回什么；iOS 无共享文件系统，自定义目录要走 `UIDocumentPicker` + security-scoped bookmark |
| **Windows** | **只能走自定义目录递归** | ⚠️ **`photo_manager` 不支持 Windows/Linux**，因此桌面端必须 `useSystemLibrary = false` 且只依赖 `includePaths` |
| macOS | 媒体库 + 任意目录 | `dart:io` 直接可读 |

这一条已写进 `LocalSourceConfig` 的文档注释。**Windows 的适配点被隔离在「扫描器如何枚举文件」这一层**，播放/入库/UI 全部共用（本项目 `playback_router.dart` 在桌面端已恒走 `media_kit`，本地文件播放无障碍）。

WebDAV 三端无差异 —— 纯 HTTP，`media_kit`（桌面）与 `just_audio`（移动）都已支持带 headers 的 URL 播放。

### 移植时的三处适配

1. **`media_cache` 包不存在于本项目**。上游 `playback_source_resolver.dart` 依赖 `AudioCacheService` + `AudioProxyServer`（本地路径包 `packages/media_cache`）。本项目有等价物：`StreamCacheService` + `MediaStreamProxy`（`media_stream_proxy.dart`，已在跑 DLNA 换签）。移植时按此映射，不引入上游包。
2. **`AppLog` 不存在**。按本项目约定换成 `if (kDebugMode) debugPrint(...)`。
3. **`bili_api` 不需要**。本项目不做 B 站音源，`playback_source_resolver` 里的 bili 分支整段去掉。

## 三、四块「免费资产」（+ 上游整仓，见「一之补」）

1. **`isLocal` 死列**（事实 3、4）：本地/云端标记位已预留，给 `SongEntity` 补字段即可。但只有它不够，还需 `sourceId`。
2. **`audio_metadata_reader` 零引用依赖**（事实 7）：本地导入最麻烦的「标签从哪来」，库已经躺在依赖里。
3. **`playlists`/`playlist_songs` 死表**（事实 6）：本地/DAV 没有服务端歌单，这两张表带索引现成可用，补个 DAO 即可。
4. **`localCoverPath`/`tagsParsed`/`localAssetId` 三个孤儿列**（事实 25、26）：语义正好是「本地封面路径」「标签已解析」「本地资源 ID」。来自上游项目 [NagoMusic](https://github.com/Keduoli03/NagoMusic)，**说明本地音源支持在上游存在过，魔改时被剥掉了**。
   ⚠️ 坑：前两个只在 `oldVersion < 2` 分支加（`db_helper.dart:219-220`），`localAssetId` 只在 `oldVersion < 8` 分支加（`:299-301`），`onCreate` 一直没有它们 → **全新安装的库反而缺列**。v18 迁移已无条件补齐（见第十三节）。

加上 `_sourceForSong` 的 else 分支（事实 5）——**本地播放链路本身是通的，只是被 `api.baseUrl.isNotEmpty` 锁死，现在飞牛和本地互斥。**

> 这四块加上「一之补」里的上游整仓，合起来指向：**本地音源不是「新功能」，是「把删掉的东西接回来」。**

## 四、逐项可行性

### 4.1 直接进入 UI —— ✅ 最容易

改 `lib/app/app.dart` 的 `_AppStartupGate` 一处：

```
现在：引导页(未完成) → OnboardingPage ；未登录 → LoginPage ；已登录 → 主界面
目标：引导页(未完成) → OnboardingPage ；无可用音源 → 首页空态引导 ；有音源 → 主界面
```

- `LoginPage`（929 行）+ FNID 探测 + 扫码配对（`login_pair_server.dart`）**全部保留**，只是入口从「启动门禁」挪到「设置 → 音频来源 → 添加飞牛」。
- `main.dart` 启动顺序有强依赖链（`AuthService.init()` → `MediaNotificationService.init()` → …），去门禁后仍要跑，但**不能再假设一定有飞牛 token**，需给 `PlayerService` 启动恢复加短路。
- 5 个相关测试需同步调整：`launch_session_behavior_test` / `login_page_tv_qr_test` / `tv_onboarding_test` / `home_back_exit_regression_test` / `first_use_large_screen_test`。

**风险：低**，有现成测试兜底。

### 4.2 本地导入 —— ✅ 可行，一个硬风险

**可复用：** 播放分支（事实 5）、`audio_metadata_reader`（事实 7）、`playback_router`（事实 17）、`MediaStreamProxy`（事实 19）、`cover_local_cache.dart`、`isAudioFileDeleted` 失效标记。

**需新建：** 目录扫描器、标签读取 + 内嵌封面落盘、本地歌单 DAO、本地收藏。

**🔴 唯一硬风险：Android 任意目录读取权限。**

Manifest 只有 `READ_MEDIA_AUDIO`（事实 11），读不到任意目录。`file_picker` 的 `getDirectoryPath()` 在 Android 走 SAF，返回的**不保证能被 `dart:io` 的 `File` 直接打开**。

| 方案 | 覆盖面 | 代价 |
| :--- | :--- | :--- |
| **A. MediaStore**（`photo_manager` 已在依赖） | 仅系统索引的音频 | **零新权限，最稳**，但覆盖不全 |
| B. SAF 目录授权 + 遍历 `DocumentFile` | 用户选的任意目录 | 要处理 `content://`，播放经 `MediaStreamProxy` 转本地 HTTP |
| C. `MANAGE_EXTERNAL_STORAGE` | 全盘任意路径 | Play 商店需单独申报，上架有阻力 |

桌面端（Windows/macOS）无此问题。

> **这条我在沙箱无法实测**（无 Android 设备、无 Flutter SDK）。必须先写 20 行探针验证 `getDirectoryPath()` 返回值能否 `File().existsSync()` 再定方案。**这是整个重构里唯一需要「先验证再动手」的点。**

**歌词：** 建议支持同名 `.lrc` 旁挂。`lyrics_repository` 已有本地 `.lrc` 缓存，加一个「先查同目录」分支即可。

### 4.3 WebDAV —— ✅ 三者里最顺

**三件事现成：** ①`backup_service.dart:366/555/724` 的连接+浏览封装；②`webdav_folder_picker_page.dart` 整个目录树 UI；③**播放根本不需要 WebDAV 协议** —— `media_kit` 支持 `Media.httpHeaders`（事实 18），直接 HTTP + Basic Auth 流播，`webdav_client` 只用于 PROPFIND 列目录。

**架构好处：** WebDAV 与本地在数据模型上同构（目录树 + 文件 + 标签），可共用扫描/入库/歌单逻辑，只有「文件访问层」不同。

**需注意：**
- **Range 请求**：拖动进度依赖 HTTP Range。主流实现（nginx dav / Alist / 群晖 / fnOS）都支持，但**必须逐服务器验证**，不支持会「能播不能拖」。
- **自签证书**：`shouldBypassSslForHost()` 是纯 host 函数（事实 20）可直接复用，但它住在 `settings_fn_state.dart`（飞牛命名）里，重构时应提到通用位置。
- **标签解析**：WebDAV 文件不能直接喂 `audio_metadata_reader`。一期先下载到缓存再解析（`StreamCacheService` 现成），二期优化为只读文件头若干 KB。
- **无服务端转码**（事实 21）：DSF/APE 只能 `media_kit` FFmpeg 软解，桌面端没问题，低端 Android 可能吃力。

**风险：低～中**，不确定性在各家服务器的 Range/PROPFIND 差异。

### 4.4 飞牛改造 —— ✅ 可行，是工程主体

飞牛链路**不需要重写，只需被包进接口**。`FeiNiuApiClient`(1438 行)、探测服务(1051 行)、转码服务(688 行)、CUE 服务全部原样保留，外面套适配器。工作量在于 24 个页面脱离 `FeiNiu*` 模型。

## 五、核心难点：耦合在页面层，不在服务层

若耦合只在 `services/feiniu/`，这次重构会很轻松。实际是页面直接绑飞牛模型（事实 12、14、15、16）。

### 难点 1：页面直接消费 `FeiNiuAlbum`/`FeiNiuTrack`

```dart
// albums_page.dart:44
AlbumGroup.fromFeiNiuAlbum(FeiNiuAlbum a)
// albums_page.dart:307
final pageData = await FeiNiuApiClient.instance.getAlbumList(...)  // → FeiNiuPageData<FeiNiuAlbum>
```

受影响：`albums_page`/`artists_page`/`genres_page`/`playlists_page`(38 处最多)/`library_detail_pages`/`home_page`/`search_page`/`songs_page`/`favorite_page`/`folders_page`/`song_edit_page`/`song_detail_sheet` 等 24 个。

**✅ 好消息（事实 29）：** 飞牛四个模型字段高度统一 —— 都是 `guid`/`name`/`coverId`/`trackCount`/`createdAt`/`updatedAt`。所以新实体**可以用完全相同的字段名 + 只加一个 `sourceId`**：

```dart
class AlbumEntity {
  final String guid;        // ← 与 FeiNiuAlbum 同名
  final String name;        // ← 同名
  final String? coverId;    // ← 同名
  final int? releaseDate;   // ← 同名
  final int? trackCount;    // ← 同名
  final int? createdAt;     // ← 同名
  final String sourceId;    // ← 唯一新增
}
```

**这样页面改动退化为：改类型名 `FeiNiuAlbum`→`AlbumEntity` + 换一次取数调用。`.guid`/`.name`/`.coverId` 全部原样可用。** `FeiNiuPageData<T>` → `LibraryPage<T>` 同理（`list`/`total`/`sort` 同名，`pageData.list` 继续工作）。**这是把 259 处引用变成机械替换的关键。**

### 难点 2：封面体系是服务端 ID

`coverId` 不是 URL，要经 `api.coverUrl()` 拼地址 + 带 Cookie（页面 18 处，事实 15）。

**解法：** 实体加 `coverUri`（可直接加载的地址/本地路径），保留 `coverId`；由音源决定填哪个；`ArtworkWidget` 统一按「有 `coverUri` 用它，否则回退 `coverId`」。**18 处调用点收敛到 1 处组件内判断。**

### 难点 3：歌手/专辑是 JSON blob + guid

`artist` 存 `[{"guid":...,"name":...,"coverId":...}]`，7 个解析方法依赖（事实 16）。

**解法：保持格式不变**（迁移成本最低），本地/WebDAV 用自生成的稳定 guid（如 `local:<hash(artistName)>`）。所有解析方法零改动，专辑/歌手聚合天然可用。**这是最省力的一个决定。**

### 难点 4：收藏/歌单/播放历史是服务端状态

- 收藏：飞牛写服务端；本地音源写 `songs.isFavorite` 列
- 歌单：飞牛走服务端；本地用那两张死表
- 播放历史：飞牛 `getPlayHistory` 走服务端；**但本地统计 `report_events` 表已经是本地的** → 统计功能天然多音源可用

**解法：** 做成**能力开关** —— `AudioSourceCaps` 暴露 `serverFavorites`/`serverPlaylists`，飞牛 true 走服务端，本地/DAV false 走本地表。UI 层无感知。

### 难点 5：转码是服务端独有能力

**解法：** 转码设置按 `caps.serverTranscode` 显隐（设置页已有大量 `if (Platform.isAndroid)` 条件渲染先例，模式一致）。高难度格式全落 `media_kit` FFmpeg —— `playback_router` 已支持。

### 难点 6：DLNA 投屏取流写死飞牛

`dlna_cast_service.dart:394`。改成 `provider.resolveStream(song)` 拿 URL+headers 交给 `MediaStreamProxy` 换签。**改动量小但必须测。**

## 七、三源并存的技术方案（本次新增的硬需求）

### 7.1 真正的难点：分页聚合

现状（事实 27、28）：**列表页完全不读 DB**，每次直连 API + `ApiCacheManager` 存 JSON blob。`songs` 表目前只被 `player_service.dart:3953/4000` 写（元数据编辑），**不是库的真相源**。

三个源并存时，无法简单拼接各自的分页结果（每源独立游标 + 全局排序 = 组合爆炸）。

### 7.2 方案对比

| | **A. 联邦查询** | **B. 本地库统一（推荐）** |
| :--- | :--- | :--- |
| 做法 | 页面问 registry，registry 扇出到各 provider 合并 | 各 provider `syncLibrary()` 全量入库，页面只查 DB |
| 分页 | 每源独立游标，跨源排序复杂 | 纯本地 SQL `LIMIT/OFFSET`，天然支持 |
| 按源筛选 | 要过滤内存结果 | `WHERE sourceId = ?`，一行 |
| 实时性 | 保持现状（每次拉服务端） | 需重新同步才见变化 |
| 页面改动 | 换取数调用 | 换取数调用 **+ 引入 `LibraryRepository`** |
| 符合事实 32 | 别扭（本地/DAV 无分页概念） | 自然（本地/DAV 本来全量） |

### 7.3 推荐：B，但用「后台同步」补齐实时性

理由：**事实 32 —— 只有飞牛有服务端分页，本地/WebDAV 目录扫描天然全量。** 强行让本地/DAV 假装支持分页是反自然的。而 B 方案下「按音源筛选」退化为一个 WHERE 子句，并存几乎零额外成本。

实时性用现成机制补：
- **下拉刷新**已存在（`songs_page.dart:558` `onRefresh: () => _loadSongs(forceRefresh: true)`）→ 改为触发对应源的 `syncLibrary()`
- **`CacheVersionStore.bump(scope)`** 已存在（`song_dao.dart:55`，`upsertSongs` 写库后 bump），页面监听即可自动刷新
- 可选：启用音源后后台静默同步（`main.dart` 里已有大量 `unawaited(...)` fire-and-forget 先例）

**⚠️ 必须如实说明的行为变化：** 飞牛服务端改了元数据，App 里不会立刻变，要下拉刷新。这是 B 方案的代价，需要你确认可接受。若不可接受，退回 A 方案（页面改动更小但分页逻辑复杂得多）。

### 7.4 并存带来的三个必须处理的细节

1. **ID 命名空间**：三源 ID 可能撞车。用前缀隔离 —— 飞牛 `guid` 原样（存量数据不动），本地 `local:<sha1(path)>`，WebDAV `dav:<sourceId>:<path>`。
2. **跨源重复歌曲**：同一首歌在飞牛和本地都有。**建议不做去重**，两条都显示并标注来源（`MediaListTile` 加来源角标）。去重规则（按 ISRC？按标题+歌手？）会引入误判，收益低风险高。
3. **来源角标 UI**：并存后用户需要知道每首歌来自哪。`MediaListTile`（`components/list/media_list_tile.dart`）加一个小标记即可。

### 顺带修掉的三个既存缺陷

改造过程中发现三处老逻辑在多音源下会直接出错，已一并修复：

**① `_sourceForSong` 取源互斥**（`player_service.dart:4036`）

旧逻辑 `if (api.baseUrl.isNotEmpty) { …飞牛全链路… }` —— 只要配了飞牛服务器，**所有**歌都按云端处理，本地文件反而播不了。这就是「飞牛与本地互斥」的根因。改为 `if (isFeiniuRemoteSong(song) && api.baseUrl.isNotEmpty)`，本地歌落到函数末尾既有的 `AudioSource.file(rawUri)`。

> **这一步做完，本地文件播放在代码层面已经打通** —— 播放链路本来就存在，只是被这个全局开关锁死。

**② 「下一首播放」会破坏本地歌的 uri**（`song_detail_sheet.dart:261`）

旧逻辑无条件把 `song.uri` 重写成 `${baseUrl}/music/api/v1/track/stream?guid=${song.id}`。本地歌的 uri 是文件路径，被换成一个不存在的飞牛地址后，「下一首播放」直接失效。同样改为按歌归属判断。

**③ 元数据编辑会静默丢列**（`player_service.dart:3993`）
